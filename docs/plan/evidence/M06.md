### (f) Risks, decisions and pending items

See §6. Summary:

- **RK-08 (cost):** `search`/`new` now read `PR_TRANSPORT_MESSAGE_HEADERS` for every item whose body is read (also `--text` candidates). Measured search op p95 0.457 s < 0.5 s on the real store; M14 SMOKE must confirm the p95 budgets. The extra COM property read per returned item is the price of A6 without a second item open.
- **New failure surface in `search`/`new`:** a COM error reading the transport headers (other than the item-unopenable ones) now propagates from `load_snippet`; before, that read only happened in `show`. Accepted for now (the plan only requires `load_headers` to be total); recorded as pending for M08/M14 if SMOKE shows it.
- **`load_headers` is not in the plugin protocol** (D-06): it is not added to `MailBackend`, only to `METADATA_OPERATIONS` so the driver proxy wraps it; `plugin_api = 1` unchanged.
- **`parse_emlx_headers` is strict about the length line** (invalid/empty/zero ⇒ `read=False`, empty headers) while `parse_emlx` recovers best effort. That is what UT-BOD-03.06 asks for; documented in `INTERFACES.md`.
- **Fake asymmetry:** the fake raises `AttributeError` for `BodyFormat` on meeting/report/task items (like `HTMLBody`); the real OOM behavior for `BodyFormat` on a `MeetingItem` is unverified on this macOS host (RK-03). Fallback is safe either way (`BodyFormat != 2` ⇒ `Body`), and M14 SMOKE on Windows is the pending real check.

## 6. Decisions and pending items

**Decisions taken (minor ambiguities, resolved with the simplest option coherent with the PRD):**

1. **Unfolded header values keep their continuation whitespace** (RFC 5322 unfolding removes only CRLF), so a folded `Authentication-Results` arrives with `\t`/space but no line break; `parse_emlx_headers` and the Outlook transport-header read use the same email policy as the message parse.
2. **`parse_emlx_headers` is strict with the container length line** (invalid, empty, non-numeric or zero ⇒ empty headers with `read=False`), while `parse_emlx` keeps its best-effort recovery. An unreadable directory or an unexpected OS error is also `read=False`.
3. **Empty header values are `None`** for `authentication_results`/`reply_to` (a present but empty header is treated as absent); the six `show` headers keep empty strings.
4. **`read` semantics:** `True` when the header block/property was read (even if the message has no such headers, e.g. internal mail), `False` when it was deliberately not read (S/MIME) or the read failed.
5. **Failure mapping:** `EmlxHeaders`/`HeaderRow` on failure carry the six header keys with empty values for Apple Mail (`_missing_headers`, matching `EmlxMessage`'s empty-header shape) and `{}` for Outlook (matching `load_body`'s transport-header behavior, where `{}` means "let `show` synthesize").
6. **The fake raises `AttributeError` for `BodyFormat` on meeting/report/task items**, mirroring the missing `HTMLBody`; the fallback is safe either way because any value other than `2` uses `Body`. The real OOM behavior for `BodyFormat` on a `MeetingItem` is unverified on this host (RK-03).
7. **`load_headers` is not added to `MailBackend`** (D-06): it stays an optional `getattr` hook of the native adapters; only `METADATA_OPERATIONS` lists it so the driver proxy wraps it like `load_snippet`.
8. **Defensive branch removed:** a `None` guard in `_header_text` was unreachable (both callers guarantee a header object), so it was deleted instead of adding a pragma; the `_parse_header_block` failure branch is covered by UT-BOD-03.06 with `message_from_bytes` patched to raise.

**Pending items / risks for the orchestrator:**

- **RK-08:** `search`/`new` now read `PR_TRANSPORT_MESSAGE_HEADERS` for every item whose body is read, including `--text` candidates. Local measurement on the real store is within budget (search op p95 0.457 s < 0.5 s), but M14 SMOKE must confirm the p95 budgets on the owner's machines.
- **New COM failure surface in `search`/`new`:** a transport-header COM error other than the item-unopenable ones now propagates from `load_snippet` (before, only `show` read that property). If M14 sees it in the field, make `_load_body` tolerate it like `load_headers` does.
- **Real Outlook `BodyFormat` on a meeting item** (RK-03) and the real `.emlx` header block layout: only SMOKE on the owner's Windows/macOS machines can confirm (HITL-03, M14).
- **`apple_mail.py` coverage** moved from 88% to 88.5% but its statement count grew by 14 (new hook and propagation); the new lines are covered except defensive branches. No action required by D-21.
- The feature branch is one **docs-only** commit behind `integration/i2-content` (`docs/plan/00-master-plan.md`, out of scope); expect the integration merge to include that file from the batch branch, not from this one.
